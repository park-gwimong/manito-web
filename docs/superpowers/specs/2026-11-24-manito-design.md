# 마니또 웹 서비스 설계

- 작성일: 2026-11-24
- 상태: 승인 대기

표기: **[합의]** 는 대화에서 사용자가 정한 것, **[제안]** 은 작성자가 정한 것으로 사용자가 바꿀 수 있다.

## 1. 의도

이미 정해진 5~10명 모임이 연말·워크숍 같은 특정 기간 동안 마니또를 진행한다. 배정하고 끝나는 것이 아니라, 기간 내내 활동이 기록되고 피드로 공유되어 분위기가 살아 있고, 종료 때 다 같이 기록과 결과를 보며 친해지는 것이 목적이다. **[합의]**

## 2. 목표 / 비목표 / 반(反)목표

### 목표
- 시작일·종료일이 있는 이벤트를 만들고 마니또를 비밀리에 배정한다. **[합의]**
- 받은 사람이 활동을 기록하고, 모두가 피드로 본다. **[합의]**
- 마니또가 그 기록이 자기 행위인지 몰래 판정한다. 결과는 종료 때 한꺼번에 공개한다. **[합의]**
- 미션을 자동으로 내려준다. **[합의]**
- 개인 참여 포인트와 모임 온도를 실시간으로 보여준다. **[합의]**
- 종료 후 한 화면에서 함께 보는 결과 발표를 제공한다. **[합의]**

### 비목표 (1차 범위 밖)
- 누구나 가입해 쓰는 공개 서비스, 회원가입·소셜 로그인
- 각자 폰에서 동시에 넘어가는 발표 화면(실시간 동기화)
- 개설자가 기간 중 수동으로 내는 깜짝 미션 (나중에 얹을 수 있게만 둔다)
- 사진 첨부, 댓글, 푸시 알림 **[제안]**
- 시작 후 중도 참여·중도 탈퇴 **[제안]**

### 반목표 (기술적으로 동작해도 실패인 것)
- **배정이 새는 것.** 화면, 네트워크 응답, 점수 변동 시점 어느 경로로도 종료 전에 "누가 누구의 마니또인지"나 판정 결과를 알 수 있으면 안 된다.
- **개설자가 계속 챙겨야 하는 것.** 시작 전 설정과 종료 때 발표 버튼 외에는 손댈 일이 없어야 한다.
- **누군가를 망신 주는 것.** 꼴찌 순위, "아무것도 안 한 마니또" 같은 지목형 표현은 발표에 넣지 않는다. **[제안]**

## 3. 제약

- 사용자 5~10명, 이벤트는 연 1~2회 수준. 성능·확장성보다 단순함이 우선이다.
- 주 사용 기기는 휴대폰. 발표 화면만 큰 화면(빔·TV) 기준. **[제안]**
- 화면 언어는 한국어, 시간대는 Asia/Seoul 고정. **[제안]**
- 배포는 NCP. **[합의]**

## 4. 접근 방식

| | 방식 | 장단점 |
|---|---|---|
| **선택** | Next.js 단일 앱 + PostgreSQL | 화면과 서버가 한 프로젝트. 비밀 정보를 서버에서만 다루기 쉽고 운영할 것이 적다. |
| | React(Vite) + Spring Boot + PostgreSQL | 스케줄러·권한 처리가 탄탄하지만 프로젝트 둘, 상시 JVM 서버가 필요해 이 규모에는 과하다. |
| | React + Supabase | 가장 빨리 뜨지만 비밀 규칙을 DB 접근 규칙으로 짜야 해서 실수 시 배정이 샌다. 핵심과 맞지 않는다. |

사용자가 1번을 골랐다. 이유: 규모가 작고 이벤트성이라 한 덩어리로 만들어 올려두는 것이 가장 덜 번거롭다. **[합의]**

## 5. 서비스 동작

### 5.1 이벤트 단계

`준비 → 진행 → 마감 → 발표 완료`

| 단계 | 전환 조건 | 할 수 있는 것 |
|---|---|---|
| 준비 | 개설 시 | 초대 링크로 입장, 이름·PIN 등록, 개설자가 설정·미션 목록 수정 |
| 진행 | 시작 일시 도달 (자동) | 참가자 확정·배정, 기록, 판정, 미션, 몰래 한 일 메모 |
| 마감 | 종료 일시 도달 (자동) | 기록·판정 불가. 마니또 추측 입력, 개설자의 발표 진행 |
| 발표 완료 | 개설자가 발표를 끝냄 | 전원이 결과와 전체 기록 열람 |

- 시작 일시에 그때까지 입장한 사람들로 명단을 확정하고 배정한다. 이후에는 입장할 수 없다. **[제안]**
- 최소 인원은 **4명**이다. 3명이면 고리 구조상 "내 대상이 아닌 나머지 한 명"이 곧 내 마니또라 비밀이 성립하지 않는다. **[제안]**
- 시작 일시에 4명 미만이면 시작하지 않고 준비 단계에 머문다. 이때는 인원이 채워져도 자동으로 시작하지 않으며, 개설자가 시작 일시를 다시 정해야 한다(늦게 오는 사람이 잘리는 것을 막기 위함). 개설자 화면에 안내한다. **[제안]**
- 준비 단계에서 개설자는 참가자를 삭제할 수 있다(이름 오타·중복 등록 정리용). 홈 화면에 현재 입장한 사람 명단을 보여줘 시작 전에 확인할 수 있게 한다. **[제안]**

### 5.2 개설과 입장 **[제안]**

- 이벤트 개설은 서버 환경변수로 설정한 **관리 비밀번호**를 아는 사람만 할 수 있다. (NCP에 공개로 떠 있으므로 아무나 방을 만들지 못하게 한다.)
- 개설 시 입력: 이벤트 이름, 시작 일시, 종료 일시, 미션 총 개수 N.
- 개설자도 참가자로 참여한다. 개설자 권한으로도 배정과 판정 결과는 볼 수 없다.
- 입장: 공용 초대 링크 → 이름 입력 → 4자리 PIN 설정. 이후 같은 기기에서는 자동 로그인, 다른 기기에서는 이름 선택 + PIN.
- PIN을 잊으면 개설자가 초기화한다. 초기화 사실은 해당 참가자의 다음 입장 때 표시한다. (개설자가 남의 계정으로 몰래 들어가는 것을 드러내기 위함)
- 개설자 본인이 PIN을 잊으면 관리 비밀번호로 개설자 PIN을 초기화할 수 있다. 이 경우에도 초기화 사실을 표시한다.
- 한 서비스에 이벤트 여러 개가 공존할 수 있다. 이벤트끼리 참가자·데이터는 공유하지 않는다.

### 5.3 배정

- 시작 일시에 서버가 무작위로 배정한다. 전원이 하나의 고리(A→B→C→…→A)가 되게 한다. 자기 자신 배정과 둘이 서로 마니또인 경우가 생기지 않고, 발표 때 고리를 따라가며 공개할 수 있다. **[제안]**
- 각 참가자는 자기 **대상**(내가 챙길 사람)만 볼 수 있다. 자기 마니또가 누구인지는 볼 수 없다.

### 5.4 기록과 피드 **[합의]**

- **받은 사람이 기록한다.** "책상에 커피가 놓여 있었어요" 같은 글을 올리면 전원의 피드에 작성자 이름과 함께 보인다.
- 기록은 글(이모지 포함)만. 작성자는 마감 전까지 수정·삭제할 수 있다. **[제안]**
- 피드의 글에는 이모지 반응을 달 수 있다. 댓글은 없다. **[제안]**
- 피드는 주기적으로 새로 불러오는 방식으로 갱신한다(실시간 연결 없음). **[제안]**

```
[피드]                         모임 온도 52.5℃  D-9
B · 오늘 14:20
  책상에 커피가 놓여 있었어요 ☕
  마니또 확인: 대기 중        ← B의 마니또에게만 [맞아요] [제가 아니에요]
  👍 3  😂 1
D · 어제
  누가 우산을 씌워줬는데… 마니또?
  마니또 확인: 완료 (결과는 종료 때 공개)
```

### 5.5 판정 **[합의]**

- 기록 작성자의 마니또에게만 그 글에 `맞아요 / 제가 아니에요` 버튼이 보인다.
- 다른 사람에게는 "대기 중 / 완료" 상태만 보인다. 결과는 종료 때까지 작성자 포함 누구에게도 보이지 않는다.
- 마니또는 마감 전까지 판정을 바꿀 수 있다. 마감까지 판정하지 않은 글은 발표에서 "미확인"으로 나온다. **[제안]**

### 5.6 몰래 한 일 **[제안, 대화에서 이의 없음]**

- 마니또는 자기가 한 일 중 대상이 기록하지 않은 것을 본인만 보는 메모로 남길 수 있다.
- 종료 때 "끝내 눈치채지 못한 선행"으로 공개된다.

### 5.7 미션 **[합의: 자동 배달 / 세부는 제안]**

- 서비스에 기본 미션 목록(30개 내외)이 들어 있다. 개설자는 준비 단계에서 추가·삭제·수정할 수 있다.
- 개설 시 정한 총 N개를 이벤트 기간에 고르게 나눈 시각에, 각 참가자에게 목록에서 무작위로 하나씩 내려준다. 한 사람이 같은 미션을 두 번 받지 않는다.
- 미션은 본인만 본다. 완료도 본인이 체크한다. 받은 미션은 마감 전까지 언제든 완료할 수 있다(다음 미션이 와도 사라지지 않음).
- 미션 내용은 "대상에게 ~하기" 형태로, 완료 사실만으로는 대상이 드러나지 않는다.

### 5.8 포인트와 모임 온도

핵심 원칙: **실시간으로 보이는 숫자는 판정 결과나 배정과 무관한 활동으로만 움직인다.** **[합의]**

실시간 개인 포인트 (기본값, 상수로 조정 가능) **[제안]**
| 활동 | 포인트 |
|---|---|
| 기록 작성 | +10 (하루 3건까지만 점수 인정) |
| 미션 완료 | +10 |

종료 때 합산되는 보너스 **[제안]**
| 항목 | 포인트 |
|---|---|
| 내 기록이 마니또 행위로 판정됨(적중) | 건당 +20 |
| 마니또로서 인정받은 선행(대상의 기록에 "맞아요") | 건당 +20 |
| 판정 참여 | 건당 +5 |
| 몰래 한 일 메모 | 건당 +5 |
| 내 마니또 추측 정답 | +50 |

- **대화에서 바꾼 점:** 판정 참여 포인트를 "하루 한 번 모아서 실시간 반영"하기로 했었으나, 그날 판정이 한 건뿐이면 점수가 오른 사람이 곧 마니또로 드러난다. 그래서 판정·몰래 한 일 포인트는 실시간에서 빼고 종료 보너스로 옮겼다. **[제안]**

모임 온도 **[합의: 공동 게이지 / 산식은 제안]**
- 36.5℃에서 시작해 모든 활동(기록, 반응, 미션 완료, 판정, 몰래 한 일)으로 오른다. 전체 합계이므로 누가 올렸는지는 드러나지 않는다.
- 인원과 기간에 맞춰 "꾸준히 참여하면 100℃ 근처"가 되도록 환산한다. 정확한 산식은 구현자가 정한다.

### 5.9 참가자 화면 구성 **[제안]**

- **홈**: 모임 온도, D-day, 피드, 기록하기 버튼
- **내 임무**: 내 대상, 받은 미션과 완료 체크, 대상이 올린 기록의 판정, 몰래 한 일 메모
- **순위**: 전원의 개인 참여 포인트를 점수순으로 표시(사용자가 실시간 공개를 원했으므로 전원 표시. 등수 숫자나 "꼴찌" 표현은 쓰지 않는다), 모임 진행 현황(전체 기록 수, 미션 완료율)
- **설정(개설자만)**: 이벤트 정보, 미션 목록, 참가자 PIN 초기화, 발표 시작

### 5.10 마감과 발표

- 마감 후 각자 "내 마니또는 누구일까?"를 한 번 고른다. 발표가 시작되면 더 고칠 수 없다. **[제안, 대화에서 이의 없음]**
- 종료 일시가 지나도 자동 공개하지 않는다. 개설자가 `결과 발표 시작`을 눌러 큰 화면에서 한 장씩 넘긴다. **[합의]**
- 발표 중 공개 데이터는 개설자의 발표 화면에만 내려간다. 개설자가 발표를 끝내면 전원의 폰에서 결과가 열린다. **[합의: 한 화면 함께 보기]**

발표 순서 **[제안]**
1. 요약: 최종 온도, 총 기록 수, 미션 완료 수
2. 한 명씩 공개(배정 고리를 따라감): "B의 마니또는… A였습니다!" → B의 기록 중 맞은 것/아닌 것/미확인, B가 몰랐던 A의 선행, B의 추측과 정답 여부 → "그럼 A의 마니또는?"
3. 시상: 보너스 합산 최종 순위(발표에서는 상위 3명만), 눈치왕(내 기록이 "맞아요"로 판정된 건수 최다), 헛다리왕(내 기록이 "제가 아니에요"로 판정된 건수 최다. 본인의 착각을 웃어넘기는 상이라 유지), 그림자 마니또(들키지 않은 선행 최다), 미션왕
4. 이후: 전체 기록과 결과를 누구나 다시 열람. 최종 점수는 전원 표시하되 순위 화면과 같은 방식으로 보여준다.

## 6. 만드는 방법

- Next.js(App Router) + TypeScript 단일 앱, PostgreSQL. **[합의]**
- NCP 서버 한 대에 Docker Compose로 앱과 DB를 함께 올린다. **[제안]**
- **비밀 정보 원칙:** 배정, 판정 결과, 몰래 한 일, 남의 미션은 서버에서만 조회하고, 요청한 사람이 볼 자격이 있는 것만 응답에 담는다. "판정 버튼을 보여줄지"도 서버가 결정해 내려준다.
- **시간 기반 처리:** 별도 스케줄러 없이, 요청이 들어올 때 "지금 시각 기준으로 밀린 전환(시작·배정, 미션 배달, 마감)"을 처리한다. 여러 요청이 동시에 와도 한 번만 처리되어야 한다. **[제안]**
- 로그인 상태는 서버가 서명한 쿠키로 유지한다. PIN은 해시로 저장한다.

### 다루는 데이터 (개념)
이벤트, 참가자, 배정(준 사람→받는 사람), 기록, 판정, 반응, 몰래 한 일, 미션 목록, 미션 배달(누구에게·언제·완료 여부), 마니또 추측.

## 7. 구현자에게 맡기는 것
